Concepts

CI and CD are two different disciplines that get lumped together.

CI vs CD

Continuous Integration: every push triggers automated build + test, catching breakage immediately. Continuous Deployment: every change that passes CI ships to production automatically (Continuous Delivery is the same but with a manual approval gate before prod).

Environment separation & rollback

Dev → Staging → Prod, each with its own config and secrets — never share a database between staging and prod. A good pipeline can roll back a deploy as fast as it rolled forward.

GitHub Actions

Workflows, jobs, steps — the concrete pieces of a real pipeline.
name: CI/CD

on:
  push:
    branches: [main]

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm test

      - name: Build & push image
        env:
          REGISTRY_TOKEN: ${{ secrets.REGISTRY_TOKEN }}
        run: |
          docker build -t syam/app:${{ github.sha }} .
          docker push syam/app:${{ github.sha }}

  deploy:
    needs: build-test
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Kubernetes
        run: kubectl set image deployment/app app=syam/app:${{ github.sha }}

Secrets live in the repo's encrypted secret store — never in the workflow file itself.

Hands-on Project

Wire a complete pipeline, from push to running pod.
git push→ CI→ test→ docker build→ push registry→ deploy K8s→ health check
  1. Automated testing — pipeline fails the build on a failing test.
  2. Docker build — image tagged with the commit SHA, never latest in prod.
  3. Image push — to a real registry (Docker Hub, GHCR, or ECR).
  4. Kubernetes deployment — kubectl set image or a Helm upgrade.
  5. Rollback — deliberately deploy a broken image, then roll back via the pipeline.
  6. Secrets — registry credentials and kubeconfig stored as encrypted secrets, not in the repo.

Cheat Sheet

on: push / pull_request
jobs..runs-on: ubuntu-latest
steps: [uses: action, run: shell command]
secrets.NAME  →  ${{ secrets.NAME }}
needs: [job1]   # job dependency
Done when: you can push a broken change on purpose and watch the pipeline catch it before it reaches production.
