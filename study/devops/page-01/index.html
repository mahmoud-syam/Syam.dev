Fundamentals

The concepts every other topic on this page assumes you already have.

Filesystem & permissions

Everything in Linux is a file, organized under a single root tree. Know what lives where before you touch anything: /etc config, /var logs & variable data, /home user files, /proc a live view of the kernel and running processes.

ls -la /etc          # long listing, shows owner/group/permissions
chmod 750 script.sh   # rwx for owner, r-x for group, nothing for others
chown mahmoud:sysadmins file.txt
umask                 # default permission mask for new files

Users, groups & sudo

User accounts live in /etc/passwd, group membership in /etc/group. Never edit /etc/sudoers directly — always visudo, which validates syntax before saving so you can't lock yourself out.

useradd -m -s /bin/bash newuser
usermod -aG sudo newuser
groups newuser
visudo

Processes & signals

Every running program is a process with a PID. Signals are how you talk to it — SIGTERM (15) asks nicely, SIGKILL (9) doesn't ask.

ps aux | grep nginx
kill -15 1234          # graceful stop
kill -9 1234            # force kill, last resort
nice -n 10 ./script.sh   # lower priority

systemd & services

Almost every modern distro boots and manages services through systemd. A unit file describes a service; systemctl is how you control it.

systemctl status sshd
systemctl restart sshd
systemctl enable sshd    # start on boot
journalctl -u sshd -n 50 --no-pager

Package management, SSH, cron

Know your distro's package manager (apt on Debian/Ubuntu, dnf/yum on RHEL-family). SSH keys beat passwords for anything you touch regularly. Scheduled jobs: cron for simple recurring tasks, systemd timers for anything that needs logging or dependencies.

apt update && apt install nginx -y
ssh-keygen -t ed25519 -C "mahmoud@syam.dev"
ssh-copy-id user@server
crontab -e
# 0 2 * * * /scripts/backup.sh   → every day at 02:00

Storage

Partitions, filesystems, and how to not run out of either disk or inodes.

Partitions & filesystems

lsblk                    # see disks & partitions
fdisk -l /dev/sda
mkfs.ext4 /dev/sdb1
mount /dev/sdb1 /mnt/data

Persistent mounts — /etc/fstab

A mount you set with mount disappears on reboot. Add it to /etc/fstab to make it permanent — always test with mount -a before rebooting, a bad fstab entry can stop a machine from booting cleanly.

UUID=xxxx-xxxx  /mnt/data  ext4  defaults  0  2
mount -a   # applies fstab without reboot — test here first

LVM (Logical Volume Manager)

Lets you resize storage without repartitioning. Physical Volume → Volume Group → Logical Volume.

pvcreate /dev/sdb
vgcreate data_vg /dev/sdb
lvcreate -L 20G -n data_lv data_vg
lvextend -L +10G /dev/data_vg/data_lv

Disk & inode usage

df can show 0% full while you're still out of space — that's inode exhaustion, usually from millions of tiny files.

df -h        # disk space
df -i         # inode usage
du -sh /var/*  # what's actually using the space

Networking

Diagnosing connectivity from the command line, layer by layer.
CommandWhat it tells you
ip addrInterfaces and their IPs
ip routeRouting table / default gateway
ss -tulnpListening ports and which process owns them
ping -c4 hostBasic reachability
traceroute hostWhich hop the traffic dies at
curl -v urlFull HTTP request/response, TLS handshake included
dig domainDNS resolution, which record type, which server answered

DNS troubleshooting order

dig domain→check /etc/resolv.conf→dig @8.8.8.8 domain→compare results

If a public resolver (8.8.8.8) resolves fine but the configured one doesn't, the problem is your DNS server, not the domain.

Logs & Performance

Where the evidence lives, and how to read system load correctly.
CommandUse it for
journalctl -xeMost recent systemd logs with explanations
tail -f /var/log/syslogLive-follow a log file
top / htopLive CPU/memory per process
free -hMemory + swap usage
vmstat 2CPU/memory/IO snapshots every 2s
iostat -x 2Disk I/O saturation per device
uptimeLoad average — 1/5/15 min

Reading load average

Load average means "processes waiting for CPU time," not "% CPU used." A load of 4.0 is fine on an 8-core box and a fire on a 2-core box — always compare against nproc.

Troubleshooting Labs

Eight scenarios. Work each one with the diagnostic flow, not the fix — the flow is the skill.

Service won't start

systemctl status svc→journalctl -u svc -n 50→check config syntax→check port conflicts (ss -tulnp)

Disk is full

df -h→du -sh /var/* /home/*→lsof +L1 (deleted-but-held files)→clear or extend

High CPU

top→identify PID→ps -o cmd= -p PID→decide: kill, renice, or scale

High memory

free -h→top sorted by %MEM→check for swap thrashing (vmstat)

High load average

uptime→compare vs nproc→vmstat 2 (CPU-bound vs IO-bound?)→iostat if IO-bound

DNS failure

dig domain→cat /etc/resolv.conf→dig @8.8.8.8 domain→isolate client vs server

Network failure

ip addr→ip route→ping gateway→ping external IP→ping domain

Broken mount

mount | grep path→cat /etc/fstab→mount -a→check UUID with blkid

Hands-on Lab

Build it once with your own hands — this is what actually makes it stick.
  1. Build 2–3 Linux VMs — one Ubuntu/Debian, one RHEL-family (Rocky/AlmaLinux) so you see both package managers.
  2. Configure SSH — key-based auth only, disable password login in sshd_config.
  3. Create users & groups — one admin user with sudo, one restricted user.
  4. Deploy a web server — nginx or Apache, serving a static page.
  5. Configure the firewall — allow only SSH + HTTP, deny everything else.
  6. Investigate the logs — find the web server's access/error logs, tail them while you curl the site.
  7. Break something on purpose — stop the service, fill the disk, kill a process — then use the flows above to diagnose it.
  8. Practice disk management — add a second disk, partition it, mount it persistently via fstab.
